# Submission

Start when: A request for a pgsql-hackers draft or patch submission materials.

1. Use [principle-pg-evidence-first](../../principle-pg-evidence-first/SKILL.md) and [prepare-pgsql-hackers-post](../../prepare-pgsql-hackers-post/SKILL.md) to establish message type, thread, patch/base and available validation. Draft-only work must not trigger implementation.

2. When attachments are requested, follow [patch packaging](../../implement-pg-patch/references/patch-packaging.md) through [implement-pg-patch](../../implement-pg-patch/SKILL.md) or [revise-pg-patch](../../revise-pg-patch/SKILL.md) as appropriate. Use genuine commit metadata and only intended changes.

3. Use [principle-pg-verify-behavior](../../principle-pg-verify-behavior/SKILL.md) to check what the evidence actually supports. Verify descriptions, versions, attachment contents and applicability; identify missing branch testing and backpatch scope.

4. Keep missing facts outside the draft. Frame insufficiently tested work as proposal/WIP and preserve technical evidence in concise prose.

Completion and output: Return the requested subject/body and verified attachment list, with factual gaps and validation limits. Stop before sending mail, posting attachments or updating CommitFest without explicit authorization.
